# Posts Feature — Integration Report

## Context

The `posts` branch of the repository contained a posts feature built with:
- Django **template-based views** (not REST API)
- Django's **default `User` model** (`django.contrib.auth.models.User`)
- A completely different folder structure (`KunuzBackend/`)

The `feature/userAuth` branch (this branch) uses:
- **Django REST Framework** with JWT authentication
- A **custom `User` model** (`apps.users.User`) with email-based auth, OTP, roles, etc.
- A clean `heritage_backend/` project layout

A raw `git merge origin/posts` would have created folder conflicts and broken the custom auth system. Instead, the posts feature was **ported and integrated** properly into the existing DRF architecture.

### 4. `apps/posts/models.py`

**Models ported from the `posts` branch with the following key changes:**
- All `ForeignKey` to `User` now use `settings.AUTH_USER_MODEL` instead of `django.contrib.auth.models.User` — this ensures compatibility with the custom `User` model.
- Fixed broken indentation in `clean()` and `save()` methods that existed in the original.
- Added `Meta.ordering = ["-created_at"]` to `Post` and `Comment`.
- Added `updated_at` field to `Comment`.
- `__str__` methods added to all models.

**Models included:**

| Model | Description |
|-------|-------------|
| `Post` | Core post with type (discovery/visit/question/alert/event), visibility, location, monument type, region, historical period |
| `EventDetails` | One-to-one extension of Post for events (starts_at, ends_at) |
| `AlertDetails` | One-to-one extension of Post for alerts (urgence_level, current_status) |
| `PostImage` | Up to 5 images per post (enforced in `clean()`) |
| `Gem` | Like/upvote reaction — unique per user+post |
| `Save` | Bookmark — unique per user+post |
| `Comment` | User comment on a post |

**Post choices:**
- `PostType`: discovery, visit, question, alert, event
- `Visibility`: public, groups
- `HistoricalPeriod`: prehistory, roman, islamic, ottoman, contemporary
- `MonumentType`: civil, military, religious, funerary
- `Region`: algiers, oran, constantine, tlemcen

### 5. `apps/posts/serializers.py`

**DRF serializers built from scratch** to match the project's response conventions.

| Serializer | Purpose |
|------------|---------|
| `PostImageSerializer` | Serializes post images |
| `EventDetailsSerializer` | Serializes event details (nested read) |
| `AlertDetailsSerializer` | Serializes alert details (nested read) |
| `PostListSerializer` | Lightweight serializer for feed/list views |
| `PostDetailSerializer` | Full serializer for retrieve/create/update — includes inline creation of `EventDetails`/`AlertDetails` via write-only fields `starts_at`, `ends_at`, `urgence_level` |
| `CommentSerializer` | Serializes comments with user display info |
| `GemSerializer` | Serializes gem reactions |
| `SaveSerializer` | Serializes saved posts |

**Key logic in `PostDetailSerializer`:**
- `validate()`: enforces that `starts_at` is provided for event posts and `urgence_level` for alert posts.
- `create()`: creates the post then creates `EventDetails` or `AlertDetails` if applicable.
- `update()`: updates the post then upserts related details using `update_or_create`.

**All read serializers expose:**
- `user_display_name` (from `user.display_name`)
- `user_username` (from `user.username`)
- Computed properties: `gems_count`, `comments_count`, `countdown_seconds`

### 6. `apps/posts/views.py`

**DRF `APIView`-based views** using the project's `api_success` / `api_error` response helpers from `apps.core.responses`.

| View | Route | Auth | Description |
|------|-------|------|-------------|
| `PostListCreateView` | `GET/POST /api/posts/` | GET: public, POST: required | List all non-deleted posts (paginated) / create a post |
| `PostDetailView` | `GET/PATCH/DELETE /api/posts/<id>/` | PATCH/DELETE: owner only | Retrieve, update, soft-delete a post |
| `PostImageUploadView` | `POST /api/posts/<id>/images/` | Required | Upload up to 5 images (multipart) |
| `GemToggleView` | `POST /api/posts/<id>/gem/` | Required | Toggle gem (like/unlike); returns `liked` + `gems_count` |
| `SaveToggleView` | `POST /api/posts/<id>/save/` | Required | Toggle save (bookmark/unbookmark) |
| `CommentListCreateView` | `GET/POST /api/posts/<id>/comments/` | GET: public, POST: required | List / add comments |
| `CommentDetailView` | `PATCH/DELETE /api/posts/comments/<id>/` | Required | Edit or delete a comment (owner only) |
| `MyPostsView` | `GET /api/posts/me/` | Required | Paginated list of the authenticated user's posts |
| `MySavedPostsView` | `GET /api/posts/saved/` | Required | Paginated list of posts saved by the authenticated user |

**Security notes:**
- PATCH/DELETE on a post checks `post.user_id == request.user.id`; staff can also delete.
- PATCH/DELETE on a comment checks `comment.user_id == request.user.id`; staff can also delete.
- `IntegrityError` on gem/save creation is caught silently to handle race conditions.
- Soft-delete pattern used for posts (`is_deleted = True`) — data is never permanently removed.

**Pagination:** `PostPagination` (20 per page, configurable via `?page_size=`, max 100).

## Testing with Postman (Frontend Guide)

### Setup

1. Open Postman → create a new **Collection** called `Heritage API`.
2. Set a **Collection Variable**:
   - `base_url` = `http://localhost:8000/api`
3. Run the server: `python manage.py runserver`

---

### Step 0 — Get a JWT Token (Auth Required for Most Endpoints)

#### Register a user

**POST** `{{base_url}}/auth/register/`

Headers:
```
Content-Type: application/json
```
Body (raw JSON):
```json
{
  "email": "test@example.com",
  "password": "password123",
  "username": "testuser",
  "display_name": "Test User",
  "expertise": "amateur"
}
```
Response → you will receive an OTP by email (or console if `EMAIL_BACKEND` is console).

---

#### Verify email OTP

**POST** `{{base_url}}/auth/verify-email/`

Body:
```json
{
  "email": "test@example.com",
  "otp": "123456"
}
```

---

#### Login

**POST** `{{base_url}}/auth/login/`

Body:
```json
{
  "email": "test@example.com",
  "password": "password123"
}
```
Response → you will receive another OTP.

---

#### Verify login OTP → get tokens

**POST** `{{base_url}}/auth/verify-login-otp/`

Body:
```json
{
  "email": "test@example.com",
  "otp": "123456"
}
```
Response:
```json
{
  "success": true,
  "data": {
    "access": "eyJ...",
    "refresh": "eyJ..."
  }
}
```

> **Save the `access` token** — add it as a Collection Variable `access_token`.

---

### How to attach the token to authenticated requests

In every request that requires auth, add this **Header**:

| Key | Value |
|-----|-------|
| `Authorization` | `Bearer {{access_token}}` |

### Upload Images to a Post

**POST** `{{base_url}}/posts/1/images/`

Headers: `Authorization: Bearer {{access_token}}`

Body → select **form-data**:

| Key | Type | Value |
|-----|------|-------|
| `images` | File | *(select image file)* |
| `images` | File | *(select another image — up to 5)* |

> Max 5 images per post. Sends `multipart/form-data`, NOT JSON.

### Gem (Like) a Post

**POST** `{{base_url}}/posts/1/gem/`

### Common Error Responses

| HTTP Code | Meaning |
|-----------|---------|
| `400` | Validation error — check `errors` field in response |
| `401` | Missing or expired JWT token |
| `403` | You don't own this resource |
| `404` | Post or comment not found (or soft-deleted) |

All error responses follow this format:
```json
{
  "success": false,
  "message": "Validation failed.",
  "errors": {
    "field_name": ["error detail"]
  }
}
```
